# 工作簿执行协调

## 复用与取舍

| 模块           | 现有实现                                    | 接入方式                                                                              |
| -------------- | ------------------------------------------- | ------------------------------------------------------------------------------------- |
| 串行队列       | Pi `src/workbook/coordinator.ts`            | 单独打包给 daemon，复用排队能力；读也经过队列，项目单独维护实际写入 revision          |
| COM 通道       | ThepExcelMCP + MCP TypeScript SDK           | 保留上游工具、schema 和 COM 执行；daemon 以一个 MCP client 连接，再向每个会话提供代理 |
| Office.js 通道 | 现有 WebSocket bridge 和任务窗格 dispatcher | 派发前排队；恢复界面也通过 bridge；结果确认使用 daemon revision                       |
| 目标与权限     | 现有工作簿身份、SDK `canUseTool`            | 路径规范化；COM 显式指定工作簿，调用前核对 FullName，保留原有审批                     |

不直接把 Pi 窗格队列标成全局协调：其 `runRead` 不等待写入，`expectedRevision` 没有实际校验，失败写入也不推进 revision。也不在 `canUseTool` 中获取长时间锁：拒绝、取消和缺失后置 hook 会留下无法判断是否仍在执行的锁。

## 保证与边界

- 同一 daemon 内、同一规范化工作簿身份的 Office.js 和 COM 操作有共同顺序；写入及可能部分提交的失败写入推进 revision。
- 写工具接受 `expected_revision`，与最近读取版本不符时拒绝派发，要求重新读取。版本仅覆盖本助手的操作，不覆盖手动编辑或其他程序。
- 每个代理会话自动记住最近一次协调读取/写入返回的 revision；模型不必手工抄写。若另一会话先写入，旧会话的下一次写入会收到 `STALE_WORKBOOK_REVISION`，必须重读。
- Stop/超时可以先结束调用者等待，但排队占用要等执行端结束；连接丢失且无法确认执行结束时阻止后续写入，不能靠超时把正在执行的写入当成已取消。
- 用户检查工作簿后，可在未知状态的工具卡片上解除写入锁；该动作推进 revision，避免旧会话沿用解除前的读取结果。
- COM 仍使用上游显式工作簿名定位；FullName 不匹配就拒绝，避免多个 Excel 实例同名文件误写。不声称因此支持任意同名跨实例路由。
- 复用上游工具的完成语义；Excel 后台刷新和外部手动修改不由 revision 代表。多个 daemon 也不共享内存队列。
