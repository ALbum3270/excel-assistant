## R1 / P0：起点写入二维矩阵再复制，目标恢复点仍然漏格

位置：`taskpane/shared/recovery.js:389`、`:392`、`:256`；调用约定见 `daemon/office-tools.mjs` 的 `prepareCellWrite()`，实际写入见 `setCellRange()`。

合法请求：

```json
{
  "sheetId": 1,
  "range": "A1",
  "cells": [[{"value": 1}, {"value": 2}], [{"value": 3}, {"value": 4}]],
  "copyToRange": "D1",
  "allow_overwrite": true
}
```

系统支持用单个起点 A1 表示由数据决定的二维写入，实际先写 A1:B2，再复制到 D1:E2。但恢复准备发生在写入前，复制目标的 `sizeFromAddress` 是字符串 `A1`，从其范围对象只能读出 1×1；没有带上 `cells` 的 2×2 形状。

**隔离复现结果：实际复制需要覆盖 4 格，目标快照只捕获 1 格。E1、D2、E2 的原内容没有进入该复制目标的恢复点。** 允许覆盖以后再恢复，将无法完整找回这些值/格式。

现有新增测试检查的是 `copyTo(A1:B2, D1)` 的覆盖保护；没有覆盖 `set_cell_range(A1, 二维矩阵, copyToRange=D1)` 的写前恢复计划。

修复方向：恢复准备须使用已解析的源矩阵最终尺寸，而非仅使用尚未写入的起点地址。保持覆盖检查、值/格式捕获、执行、回执采用一致的实际区域。

## R2 / P0：撤销 → 重做 → 再撤销时，行结构与数据顺序错误

位置：`taskpane/shared/recovery.js:1267`。

```js
const undoingARestore = group.every((item) => item.restoredFromSnapshotId);
```

只要快照来自一次 restore，此条件就为真。二次、三次乃至更多次反向快照均含 `restoredFromSnapshotId`，因此排序永远固定为“值先、结构后”，不会随着逆操作改变。

用实际 `workbookHistory()` 分组调度、实际 Pi `restoreWorkbookRecoverySnapshot()` 配合内存中的单列工作表复现：

| 步骤 | 工作表内容 |
| --- | --- |
| 原始数据 | A、B、C |
| 删除第 2 行 | A、C |
| 第一次恢复（撤销删除） | A、B、C，正确 |
| 恢复其反向恢复点（重做删除） | A、C，正确 |
| 再恢复最新反向恢复点（再次撤销删除） | **A、B、B、C，重复了一行** |

第三次先向未插行的区域写回 A/B/C，再插回 B，造成重复。此处 Excel 边界是内存桩，分组、排序和反向快照生成均执行当前源码；没有声称真实 Excel 已实测该序列。

现有 `recovery-restore.test.mjs` 验证的是两个值快照是否共用 toolCallId，没有验证值+结构的连续往返。

修复方向：记录并正确反转一次组内恢复的实际执行顺序/方向，不能只判断“是否存在恢复来源”。至少核对三次连续往返后的数据及公式位置。

## R3 / P1：COM 前置 info 被真正取消时，零写入也会锁住工作簿

位置：`daemon/thepexcel-gateway.mjs:226`、`:231`；`daemon/workbook-execution.mjs:155`。

新 gateway 把 signal 传给 info 请求，但只在 await 正常返回后调用 `stopIfCancelled()`。实际 MCP client 收到取消会拒绝 Promise，执行不会到达该检查。

传回协调器的取消异常没有明确的 `not_committed`/已结束状态；协调器按可能发生写入处理，增长 revision 并留下 blocked。后续合法写入因 `WORKBOOK_UNCERTAIN` 被拒绝，尽管 COM 写工具从未派发。

**使用实际 gateway 与协调器，配合响应 signal 的 MCP client 桩复现：写调用数 0、revision 1、blocked=true，下一次写入得到 WORKBOOK_UNCERTAIN。** 所安装 MCP SDK 的 signal 拒绝路径可见 `node_modules/@modelcontextprotocol/sdk/dist/esm/shared/protocol.js` 约 709 行。

现有 COM 回归的 info 桩忽略了 signal，等待人工 release 后成功返回，因此只测到了 `stopIfCancelled()` 能运行的那条分支。

修复方向：区分“写操作尚未派发”与“已经派发、结果未知”。前置步骤的取消或失败应明确表示未提交，并结束该次协调；不能一律套用写入中断的不确定状态。
